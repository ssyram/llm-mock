# Mock 平台的问题意识与前提

## Q.I：pi-ai / pi-messages 协议的对偶实现

本轮用户明确确认：

> 因此 Q.I 就是一个 pi-ai / pi-messages 协议的对偶实现

根源问题是缺少足够稳定、AI 可以快速开发和验证的 Mock 平台。平台把厂商封装留在基础设施中，使后续开发集中在脚本本身；脚本只面对统一内容，不需要分别处理 GPT、Google、Anthropic 等平台的 wire。

这是一条 Q.I，不把协议数量、trait 形式、测试数量或某种测试技术另立为并列意图。具体哪些协议已支持、如何实现与验证，由设计承接，不用当前测试覆盖反过来定义用户只想要什么。

## Q.A：用于设计论证的前提

- pi-ai 已有统一 Message 模型、厂商请求构造与回复解析；pi-messages 随同一源码树提供。它们可作为服务端反向转换及对偶实验的参照，不等于现成提供服务端转换。
- 对偶行为依赖具体参照版本。同名版本号不保证源码相同，因此判断对偶需要确定、可重现的参照；当前选择和检验机制见 architecture.md。
- 厂商表示存在不携带、合并、变换和运行时注入的字段。对偶应依据逐协议精确定义的 canonical/providerFill，而不是假定所有原始字段可逆；wire 已携带而服务端漏读，不能仅因当前模型缺字段就称为信息论丢失。

这些前提支撑设计，不自行新增用户意图。特别是“已有 pi-ai”不推出其他客户端所有扩展都已被证明兼容，也不推出一组通过的样本已经覆盖全部声明义务。

## 从前提到设计性质

用户同时明确：

> Q.A 包括了一定要锁版本等内容，也可以是 P

本项目保留其两种作用：确定参照是认知前提；开发与验证必须锁定并校验参照是 `P.ref`。Git submodule、具体 commit、依赖 lockfile 和检查命令，是落实该性质的 D/I，不是另一条 Q.I。

此前已经明确的 Rust/Cargo 独立使用、缺依赖仅跳受影响测试组、环境齐全全自动运行、真实失败不得跳过等约束，也在根设计的 `P.workflow` 中承接，不因整理 Q 而丢掉或重新要求用户逐项决策。
